# Completion protocol

This is the Moonstone completion convention. Clingy is its reference
implementation, not its owner: any tool that answers these two hidden
endpoints — regardless of language or framework — gets the same shell
integration any Clingy app gets, including from consumers that have never
heard of Clingy specifically.

There are two endpoints, for two different jobs:

- `--__moonstone-complete-script <shell> [cmd_path]` prints the shell
  bridge itself — the same text `app:completion_script(shell, cmd_path)`
  returns. A human runs this once, the same way they would for any CLI
  (`meteorite completions zsh >> ~/.zshrc`, or dropped into their shell's
  completion directory). A consumer can also call it *lazily*: `moon
  exec`'s own completion delegation, the first time it needs to complete
  arguments for a command nothing has registered a completion for yet,
  calls this endpoint, `eval`s the result, and only then defers to the
  shell's own normal completion dispatch (`complete -p`, `_normal`,
  `complete -C`) — exactly as if that registration had always been
  there. Either way, the actual protocol parsing below lives in exactly
  one place: the generated bridge itself. No consumer needs to know the
  wire format to benefit from it.
- `--__moonstone-complete <shell> <words...> --cword=<index>` is what a
  bridge generated by the endpoint above calls internally, on every
  keystroke, to get real candidates. This is the one described in detail
  below — but only the generated bridge itself should ever need to speak
  it directly.

Shell bridges invoke the application through the query endpoint:

```text
<binary> --__moonstone-complete <shell> <words...> --cword=<index>
```

`--__clingy-complete` is accepted as an alias, for compatibility with shell
bridges generated by older Clingy versions; new bridges emit
`--__moonstone-complete`.

`words` is the command line through the cursor, including the executable. An
empty active word may be omitted as long as `cword` points one position past
the supplied words. `cword` is 1-based. Bridges remove shell quoting from
completed words and preserve the active word's insertion prefix.

The endpoint runs before parsing, handlers, lifecycle stages, and presentation.
Protocol version 2 uses typed, tab-separated records:

```text
V<TAB>2
D<TAB>filenames,nospace<TAB>file<TAB>--config=<TAB>lua,luax
C<TAB>--config=src/main.lua<TAB>Lua entry point
```

- `V` declares the protocol version.
- `C` carries an insertion value and optional description.
- `D` carries directives, filesystem kind, replacement prefix, and allowed
  extensions. `-` means the field is absent.

The directives are `filenames`, `dirnames`, `nofiles`, and `nospace`.
Filesystem kind is `path`, `file`, or `directory`.

Colons, spaces, quotes, and backslashes are ordinary field content. Candidate
values cannot contain NUL, tab, CR, or LF because those bytes delimit records;
descriptions normalize those control characters to spaces.

`App:complete({ words = ..., cword = ... })` returns the structured response
before rendering. `App:completion_script` and
`c.completion.completion_script` generate the shell bridges.
